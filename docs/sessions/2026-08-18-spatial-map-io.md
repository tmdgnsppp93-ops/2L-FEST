## 1. 비트 핀 재현 실험 — 스택을 맞춰도 통과하지 않는다

`docs/WORKLOG.md` §1-1이 본문이고, 여기에는 **결론에 이른 경로**만 적는다.

시작은 단순한 확인이었다 — 다른 PC에서 기록된 `147 passed / 6 xfailed`가 맥북에서
재현되는지. 맥북은 **145 passed / 8 xfailed**가 나왔고, 차이는 비트 핀 2건
(`test_default_pin` / `test_legacy_pin`)이 스택 불일치 xfail로 내려간 것뿐이었다.
`conftest.PINNED_STACK`이 python 3.14.3 / numpy 2.4.3 / scipy 1.17.1인데 맥북은
3.12.13 / 2.4.6 / 1.18.0이라 게이트가 걸린 것이다. 여기까지는 예상대로였다.

그래서 **핀 스택을 그대로 재현한 venv를 만들었다**(python-build-standalone
prebuilt, sha256 검증, 소스 빌드 아님):

```
인터프리터  ~/.local/share/2lfest-pin/python/bin/python3.14
venv        ~/.venvs/2lfest-pin        (저장소 밖 — 유지 중)
스택        3.14.3 / 2.4.3 / 1.17.1    = PINNED_STACK 완전 일치
```

`stack_mismatch()`가 `None`이 되어 xfail이 풀리고 strict로 실행됐다. **그런데 둘 다
값 불일치로 실패했다.**

| 테스트 | 지점 | 상대 편차 |
|---|---|---|
| `test_default_pin` | PINS[0] (Vb=0) | 통과 (≤1e-8) |
| `test_default_pin` | PINS[1] (Vb=0.85·Voc) | 1.70e-7 |
| `test_legacy_pin` | PINS[0] (Vb=0) | 통과 (≤1e-8) |
| `test_legacy_pin` | PINS[1] (Vb=0.85·Voc) | 9.75e-7 |

**결론: `PINNED_STACK` 3종은 비트 재현의 충분조건이 아니다.** Vb=0은 맞고 바이어스가
걸리는 지점부터 벌어지며, 편차 크기는 `conftest`가 "SuperLU·BLAS 차이만으로 뜬다"고
적어둔 범위와 같다. 남은 차이는 OS·BLAS/LAPACK·SuperLU 빌드 등 **`PINNED_STACK`이
기록하지 않는 축**이다(맥: numpy=Accelerate, scipy=번들 OpenBLAS, aarch64/darwin).

**원 캡처 머신이 무엇이었는지 저장소에 기록이 없어** 원인을 특정하지 못했다.
v28.46 커밋 메시지도 버전 3종만 적었다. → **다음 재캡처 시 OS·아키텍처·BLAS 백엔드까지
반드시 함께 기록할 것.** 그러지 않으면 이 실험을 또 반복하게 된다.

**하지 않은 것:** `PINNED_STACK` 수정, `conftest` 수정, 기준값 재캡처, 시스템 python
변경. 전부 사용자 지시로 금지됐고, 실측 결과도 그 판단을 지지한다 — 재캡처하면

## 4. 비트 동일이 성립하는 구조

계획서에 적었고 테스트로 고정한 근거. **두 겹 모두 "1을 곱함"이 아니라 "곱셈을 아예
하지 않음"에 기댄다.**

1. `dp.spatial_*` 기본값이 `None`이고, `_spatial_mult`가 `None`을 반환하면 소비
   지점 4곳이 전부 `if ... is not None:` 가드 안이라 **부동소수점 연산이 하나도
   추가되지 않는다.**
2. 예외인 bottom-cell 경로만 리터럴 `1.0` 곱인데 IEEE 754에서 정확하다 —
   Metal Optical Transparency의 `optical_widths()`와 같은 논리.

**따라서 GUI의 맵 해제는 반드시 `dp.spatial_x = None`이어야 한다.** uniform 맵으로
대체하면 값은 같아도 (1)의 가드를 우회해 근거가 사라진다. 이 규칙은
`test_clearing_map_to_none_restores_bit_identical_result`가 지킨다.

## 5. 단위 0~2 진행과 발견

### 단위 0 — 특성화 테스트 (30건, 프로덕션 0줄)

**발견 ①: `SpatialMap` 테스트가 저장소에 하나도 없었다.** 엔진은 완성돼 있는데
회귀 감시가 없는 상태였다. 로더를 붙이기 전에 현재 동작을 먼저 고정해야 이후
단위에서 무엇이 회귀인지 판정할 기준이 생긴다 — 그래서 단위 0을 여기에 뒀다.

교차검증에 직결되는 두 규약의 **우리 쪽 값**을 못 박았다:

- **꼭짓점 정렬** — `linspace(0,H,ny)`이므로 `matrix[0]`이 `y=0` 경계. 픽셀 중심이
  아니다. `[[1,2],[3,4]]`로 네 모서리를 각각 구분해 확정.
- **행 방향** — `matrix[0]` = `y=0`. 텍스트 파일 첫 줄을 사람은 위쪽으로 읽으므로
  Griddler가 첫 줄을 `y=H`로 보면 상하 반전된다.

30개 모두 첫 실행에 통과했다. 특성화 테스트치고 드문 결과지만, 엔진이 이미 완성돼
있고 배선만 없던 상태라 앞뒤가 맞는다.

### 단위 1 — 캐시 무효화 정정 (v28.56)

**발견 ②: 캐시 무효화가 `id()` 기반이었다.** `_build`의 `_sm_tag`와 `_spatial_mult`의
배열 캐시가 맵의 **주소**로 변경을 감지했다(주석도 "cheap id()-based tag"라고 인정).
지금까지 안전했던 이유는 **앱이 맵을 생성·소멸시킨 적이 없어서**다 — 즉 이 작업이
만들려는 바로 그 기능이 전제를 깨뜨린다.

지시받은 순서(재현 → 정정 → 확인)대로 진행했고, **재현 경로가 둘로 갈렸다**:

- **제자리 수정**(`sm.background = 2.0`) — id 불변이라 **결정론적으로 실패**. 실제
  엔진에서 `Gc` 비율이 0.5여야 하는데 1.0이 나왔다. GUI가 target당 맵 하나를 두고
  필드만 갱신하면 **100 % 이 경로**다.
- **주소 재사용**(A 해제 → B 생성) — 단독 실행에서는 20/20 재사용됐으나 **pytest
  안에서는 할당 패턴이 달라 재현되지 않아 수정 전에도 통과했다.**

→ 확률 의존이 실제로 확인됐으므로, 주소 재사용 시나리오는 회귀 가드로만 두고
**실패 입증 책임은 제자리 수정 테스트와 `content_key()` 계약**이 지게 했다.
`_sm_tag`는 `_build`의 지역 변수라 직접 못 읽으므로, 태그의 **재료**인
`content_key()`를 결정론적으로 검사한다(같은 내용 → 같은 키, 13개 필드 각각 바꾸면
다른 키). id() 기반은 "별개 객체는 항상 다른 id"라 이 계약을 결정론적으로 위반한다.

정정: `SpatialMap.content_key()` = mode + 스칼라 13개 + 행렬(형상 + sha256).
**맵이 없으면 예전처럼 `0`으로 태그**하므로 무맵 경로는 거동·비트 동일·비용 모두
불변이다. 과잉 무효화 방지도 함께 고정했다(`_Gc` 객체 동일성으로 조기 반환 판정).

### 단위 2 — txt/csv 로더 (v28.57)

`load_spatial_map_txt(path, *, delimiter=None) -> SpatialMap`. 테스트 26건을 먼저
작성해 전부 실패시킨 뒤 구현했다. **호출처 0 — 앱 동작은 이전과 완전히 같다.**

- 절대값 규약을 테스트로 고정(`10,20/30,40` → 평균 25 그대로).
- **값 제약을 로드 시점에 끝낸다** — 0·음수·NaN·inf(±)를 클램프·치환 없이
  파일명·행·열·값을 적어 거부. `evaluate()`가 솔버 실행 중에 던지면 사용자는 어느
  파일의 어느 칸이 문제인지 알 수 없다.
- 관용 입력 흡수: BOM(utf-8-sig, v28.20 전례)·CRLF·빈 줄·`#` 주석·줄 끝 구분자.
- `load_report`(경로·형상·구분자·건너뛴 줄·경고) — DXF 로더의 `report` 관용구.
- 이미지는 규약이 반대라 **별도 함수**로 두고 확장자 분기를 넣지 않는다고 도크스트링에
  못 박았다. 한 함수 안에서 절대/상대가 섞이면 나중에 구분이 흐려진다.
