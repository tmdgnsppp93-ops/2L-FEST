## 1. 단위 3 — Griddler 대조는 **할 수 없다**

계획의 단위 3은 "같은 4×4 행렬을 Griddler 2.5에 넣어 격자 정렬과 행 방향을 대조"
였다. 앞 세션이 절차서·시험 행렬·기대값 8점까지 준비해 두고 측정만 기다리고 있었다.

**측정 자체가 불가능하다. Griddler 무료판에 공간 분포 입력 기능이 없다 — PRO 전용이다.**

| 근거 | 내용 |
|---|---|
| 벤더 비교표 | *"Input spatial property distributions as txt or TIFF"* → **Free = NO** |
| 매뉴얼 §3.1 | Nonuniform cell parameters를 **PRO 기능**으로 기술 |
| 실물 확인 | 무료판 화면에 **진입점(파라미터 옆 canvas 버튼) 자체가 없다** |

절차서 §4는 *"파라미터 옆 버튼 → canvas → Enable 체크 → Import pattern"*으로
시작하는데, 그 버튼이 없으므로 절차를 **시작할 수조차 없다.** 우회로도 없다 —
값을 손으로 넣는 방식은 비균일 분포를 만들지 못하고, DXF import는 금속 패턴이지
물성 분포가 아니다.

### 왜 "미판정"으로 두지 않고 확정했나

박사님 지시대로 규약을 **자체 규약으로 확정 선언**했다 —
`docs/spatial_map_convention.md`.

미판정으로 두면 이후 모든 단위가 *"규약이 아직 안 정해졌다"*를 이유로 멈춘다.
그리고 실제로 미룰 이유가 없다: **이것은 이미 엔진이 하고 있는 동작이고**
(`SpatialMap.evaluate()`의 csv 분기), **단위 0의 특성화 테스트 30건이 그 동작을 이미
고정**해 두었다. 확정 선언은 새 동작을 만드는 것이 아니라 **있는 동작을 공식 규약으로
승격**하는 일이다.

```
matrix[0] = y = 0      첫 데이터 줄이 셀의 아래쪽
꼭짓점 정렬             linspace(0,H,ny) — 모서리 값이 셀 모서리에 정확히
```

`linspace`가 주는 꼭짓점 정렬은 그 자체로 합리적이기도 하다. 사용자가 "모서리를
2.0으로 하고 싶다"고 하면 그대로 2.0이 된다. 픽셀 중심이면 모서리에서 clip이 개입해
값이 흐려진다.

### ⚠ 선언과 확인은 다르다

**지금 상태는 "우리 규약을 명시적으로 선언했다"이지 "Griddler와 일치함을 확인했다"가
아니다.** 이 구분을 흐리면 안 된다 — **발표·보고에 교차검증으로 쓸 수 없다.**
PRO를 확보해 대조해야 후자가 된다. 규약 문서와 계획서 양쪽에 이 경고를 박아 두었다.

### 지우지 않고 보존한 것

박사님 지시대로 절차서(`docs/crosscheck/`)를 **그대로 뒀다.** PRO가 생기면 §4부터
바로 이어서 실행할 수 있게, §7 말미에 **재개 절차 4단계**를 적어 두었다.

여기에 하나 더 했다 — **절차서 §2의 기준값 8개를 테스트로 묶었다**
(`test_crosscheck_4x4_matches_documented_expectations`). 그 표는 PRO 대조 때 우리 쪽
기준선인데, 그때까지 코드가 바뀌어 문서와 어긋나면 **대조 자체가 무의미해진다.**
문서와 코드가 같이 움직이도록 한 것이다. 시험 행렬의 비대칭성도 함께 고정했다
(대칭이면 두 오류가 모두 감춰진다).

### 뒤집힐 경우의 처리 — 로더 안에서만

향후 대조에서 어긋나면 **보정은 `load_spatial_map_txt` 안에서만** 한다.
`SpatialMap.evaluate()`는 어떤 경우에도 건드리지 않는다.

**이유는 회귀 기준의 독립성이다.** `evaluate()`를 고치면 단위 0의 특성화 테스트
30건이 깨지는데, **그 테스트가 바로 회귀 감시 기준이다.** 기준을 같이 움직이면
무엇이 회귀인지 판정할 수 없게 된다. 부수적 이유 하나 더 — `evaluate()`는 파일뿐
아니라 **메모리에서 직접 만든 행렬**(스크립트·`_audit.py`)도 받는다. 거기에 파일
포맷 보정을 섞으면 두 입력 경로의 의미가 갈린다. 보정은 파일 경로에만 속한다.

## 2. 단위 4 — GUI 배선 (v28.58)

### 계획 대비 편차: 사이드바에 펼치지 않고 별도 창으로

계획은 *"4종 각각에 대해 파일 선택 버튼, 현재 파일명 표시, 해제 버튼, 미리보기"*를
사이드바에 두는 그림이었다. **그대로 하면 세로가 넘친다** — 4 × (파일명 + 3버튼 +
힌트)이고, 사이드바 세로 넘침은 `_gui_i18n_check.py`가 감시하는 항목이다.

그래서 사이드바에는 **진입 버튼과 요약("4개 중 n개 적용")만** 두고 조작은
`_open_spatial_maps` 창으로 뺐다. 부수 효과로 미리보기 캔버스가 제대로 들어간다 —
사이드바 폭 260 px에 컬러바 달린 그림을 넣는 것은 애초에 무리였다.

### 진입점을 모듈 수준에 둔 이유

GUI 콜백 안에 `setattr`을 흩어 놓지 않고 모듈 수준 함수로 모았다:

```
set_spatial_map / clear_spatial_map / get_spatial_map / active_spatial_maps
spatial_map_caption / draw_spatial_map_preview / SPATIAL_TARGET_INFO
```

두 가지를 얻는다. **(1) "맵 없음 = None" 규칙을 한 곳에서 강제**할 수 있다.
**(2) Tk 없이 테스트된다** — GUI 콜백은 이들을 부르기만 하므로 얇다.

### 지킨 계약 셋

**① 해제는 반드시 `None`이다.** `SpatialMap(mode='uniform')`으로 대체하면 값은 1.0
으로 같지만 `_spatial_mult`가 노드 길이 배열을 만들어 **실제 곱셈이 실행된다.**
무맵 경로의 비트 동일 근거는 *"1을 곱한다"*가 아니라 **"곱셈을 아예 하지 않는다"*
(소비 지점이 전부 `if ... is not None:` 가드 안)이므로, uniform 대체는 그 근거를
없앤다. `clear_spatial_map`이 강제하고, 로더를 경유한 부착→해제 왕복이 **비트
동일**임을 테스트가 확인한다.

**② 부착은 인스턴스에만.** `spatial_*`는 `DiodeParams`의 **클래스 속성**이라
클래스에 붙이면 이후 만들어지는 모든 인스턴스가 물려받는다 — `solve()` 내부 폴백
`dp = DiodeParams()` 경로까지 전부. 되돌리기 어렵고 *"맵을 지웠는데 결과가 그대로"*
로 나타난다. `_check_spatial_dp`가 `TypeError`로 즉시 막는다. 실제 부착 대상은
**전역 `DP` 인스턴스**다 — GUI의 `calc_iv` 호출이 전부 `DP`를 넘기기 때문이다.

**③ 미리보기는 `origin='lower'`.** `matrix[0]`이 `y=0`(셀의 아래쪽)이므로 기본
`origin='upper'`로 그리면 **화면이 규약과 정반대**가 되고, 사용자는 그걸 보고 파일을
거꾸로 만든다. 격자점 오버레이를 함께 찍어 **꼭짓점 정렬이 그림으로 보이게** 했고,
*"편집기에서 본 것과 위아래가 반대인 게 정상"*이라는 안내를 캡션에 붙였다.

### rc 라벨 — 의미가 반대다

`rc` 맵은 **접촉 저항 R을 곱한다**(컨덕턴스 `Gc`를 나눈다). 사용자가
*"1.5 = 접촉이 1.5배 좋아짐"*으로 읽기 쉽다. 계획이 확정해 둔 문구를 i18n 키로
넣고 **앰버색**으로 띄웠다 — 나머지 셋과 색이 다르면 눈이 먼저 간다.

```
접촉 비저항 배율 (rc) — 값이 클수록 접촉이 나쁨
  0.5 = 접촉저항 절반 (잘 눌린 영역)
  2.0 = 두 배 (덜 눌린 영역)
```

방향 자체는 `test_rc_map_multiplies_resistance_not_conductance`가 고정하고, **문구가
방향을 말하는지**는 `test_rc_label_states_the_inverted_meaning`이 지킨다.

### i18n에서 밟을 뻔한 함정

`_update_sidebar_labels`의 `_card_headers`는 `[before, after, grid, diode]` **4개
위치 고정 zip**이다. SPATIAL MAPS 헤더를 거기 append하면 다섯 번째가 되어 라벨이
**조용히 엇갈린다**(zip은 짧은 쪽에서 끊기므로 오류도 안 난다). `_spatial_card_hdr`
로 따로 참조해 갱신한다.

> ⚠ **알려진 한계**: 맵 설정 창이 **열려 있는 동안** 언어를 바꾸면 그 창의 라벨은
> 그대로다(닫았다 열면 갱신). 창이 모달이 아니라 생기는 한계이며, MODEL 창에도 같은
> 성격의 제약이 있다 — 그쪽이 자체 lang 토글을 둔 이유다.

## 3. 발견 — 미리보기 폴백이 없는 속성을 읽고 있었다

`_cell_extent_cm`의 폴백이 `GEO.cell_w` / `GEO.cell_h`를 읽었는데, **`CellGeometry`의
속성명은 `W` / `H`다**(`cell_w`는 **생성자 인자 이름**이고 속성으로 남지 않는다).

**입력란이 비거나 숫자가 아닐 때만 타는 경로**라 화면으로는 보이지 않는다. 잡은 것은
**Tk 목 위에서 콜백 본문을 실제로 실행하는 스모크 8건**이다 — `object.__new__`로
`__init__`을 우회한 인스턴스에 필요한 것만 붙이고 메서드를 직접 호출한다. 위젯 호출은
목이 삼키고 그 사이의 파이썬 코드는 진짜로 돈다.

계약 테스트(부착·해제·규약)만으로는 **창 빌더와 콜백 본문에 닿지 않는다.** 거기
오타가 나면 버튼을 눌러야 발견된다. 이 8건을 따로 둔 이유다.

## 5. 단위 5 — 문서·등록 자료 마무리

계획의 마지막 단위다. 코드는 건드리지 않았다.

### 버전은 올리지 않았다

계획은 "단위 5에서 `__build__` 올림"이었으나 **이미 v28.58이다.** 단위 1·2·4가
프로덕션 동작을 바꿀 때마다 그 자리에서 올렸기 때문이다(단위 1의 계획 대비 편차).
문서만 바꾸는 단위에서 버전을 올리면 **"동작은 같은데 버전만 다른" 상태**가 되어
단위 1이 피하려던 것과 정확히 반대가 된다. `_build_sha()`는 파일 해시라 값이
바뀌지만 계산 결과와 무관하다.

### pro_feature_map #6 — "구현"이되 **자체 규약**임을 판정 문구에 넣었다

감사 문서는 읽기 전용 원칙이라 **원 판정을 지우지 않았다.** 머리에 개정 이력 표를
신설하고, #6 상세에 개정 블록을 얹은 뒤 원문을 *"원 판정 (2026-08-14, 보존)"*으로
남겼다. 집계 줄도 원 집계를 병기했다.

판정 문구는 그냥 "구현"이 아니라 **"구현 (txt/csv, 자체 규약)"**이다. 이 항목에서
가장 중요한 구분이기 때문이다:

| | 뜻 | 이번 상태 |
|---|---|---|
| **기능적 대응** | 같은 목적을 같은 입력 형식으로 달성 | ✅ 달성 |
| **호환** | 같은 파일이 양쪽에서 같은 결과 | ❌ **미확인** (대조 불가) |

상세 절에 규약 3항목(행 방향·격자 정렬·값 해석) 각각을 "Griddler와 같은가 → 미확인"
으로 표에 못 박았다. *"같은 파일을 두 도구에 넣으면 결과가 일치한다"는 주장은 하지
않는다*를 문장으로도 남겼다 — 감사 문서는 나중에 인용되는 문서라 여기서 흐리면
인용하는 쪽에서 되돌릴 수 없다.

부수로 하나 고쳤다: 판정표의 "비고 B"가 **가리키는 항목이 없었다**(비고가 A → C로
건너뛴다). `§#6 상세`를 가리키게 했다.

### registration_material.md — 재현성 한계를 서술로 넣었다

수치는 스크립트가 재생성한다(테스트 **147 → 258**, 규모·버전·커밋). `--check` 통과.
§2-5 기능 목록에 비균일 공간 분포 입력을 추가했다.

**§5-1에 "비트 재현성의 범위" 절을 신설했다.** 등록 자료는 대외 문서라, 재현성을
무조건 보장한다고 읽히면 곤란하다. 실험으로 확인한 그대로 적었다:

- **버전 3종(Python/numpy/scipy) 고정만으로는 비트 재현이 보장되지 않는다.** 캡처
  시점과 완전히 동일한 버전 조합을 재현한 환경에서도 값이 일치하지 않았다.
- 남는 축은 **CPU 아키텍처와 BLAS 구현** — x86-64 + scipy 번들 OpenBLAS vs
  aarch64 + Apple Accelerate. 편차는 **상대 1e-7 수준**.
- **편차가 드러나는 방식에 규칙성이 있다**: 단락 조건(V=0)에서는 나타나지 않고
  **바이어스 조건에서만** 나타난다. 뉴턴 반복이 누적되며 최하위 비트 차이가
  증폭되기 때문이다. 물리 모델이 아니라 부동소수점 산술의 성질이다.

그리고 이것이 결함으로 읽히지 않도록 **재현성을 두 층으로 관리한다**는 정리를
붙였다 — 비트 동일성(캡처 환경 한정, 리팩터링 검증용) / 물리적 동등성(환경 무관,
결과 해석용). 스택 게이트가 그 둘을 자동으로 갈라 준다는 것도 함께.

§5-1의 xfail 서술에 모순이 있어 함께 고쳤다 — 문장은 "8건"인데 생성 수치는 "6건"
이었다. 머신에 따라 갈리는 값을 문장에 박아 둔 탓이다. 스택 게이트가 걸리는
환경에서만 8건이 됨을 명시했다.

§5-2(Griddler 대조)에는 **대조하지 못한 항목**을 명시했다. 대조한 것만 적고 못 한
것을 적지 않으면, 읽는 쪽은 전부 대조된 것으로 읽는다. §7 한계에도 두 줄 추가했다.
